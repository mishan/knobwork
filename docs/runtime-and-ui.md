# Runtime performance, resilience, and UI findings

## Guiding priorities

Boot-time optimization is intentionally low priority. The useful optimization
targets are:

1. UI responsiveness and predictable interaction latency.
2. Runtime memory/CPU pressure.
3. Recovery from missing resources, malformed messages, and failed services.
4. Better diagnostics without excessive synchronous logging.
5. Interface improvements that remain reversible.

## JavaScript loading resilience

`jci/gui/framework/js/Utility.js` is byte-identical in 70.00.100A and
74.00.324A. `Utility.prototype.loadScript` creates a script element, assigns an
`onload` handler, and appends it to the document head.

The stock implementation has no observed:

- `onerror` handler;
- timeout;
- duplicate-load suppression;
- retry or fallback path;
- failure callback;
- structured record of the resource that blocked startup.

The reversible Developer Diagnostics integration now wraps that stock method
without replacing `Utility.js`. It preserves the existing success callback and
load ordering, adds an idempotent `onerror` path, and retains the latest 80
structured outcomes in `window.__cmuScriptLoaderDiagnostics`. Callers are
required by default. The example application is explicitly optional: if its
script fails, the integration removes its Applications entry, discards only
messages targeting that app, clears its loading bookkeeping, and returns the
framework to Applications in the idle state. Required stock scripts continue
through the factory state-timeout/restart policy.

No loader timeout was added. A timeout should be introduced only after
measuring legitimate CMU load times.

Remaining loader work before considering a broader framework patch:

- measure stock and overlay resource-load latency on real hardware before
  selecting any timeout;
- decide whether retry is safe for any individual resource class;
- connect optional-app failures to a persistent/browser-readiness signal once
  that signal is proven on a bench CMU; and
- consider a stock `Utility.js` patch only if multiple applications need the
  contract and the overlay hook is no longer sufficient.

## v74 WebSocket ordering code

`jci/gui/framework/js/Websockets.js` adds sequence/reordering behavior not
present in the same form in 70. The implementation is syntactically valid but
has several suspicious semantic defects:

- Calls use `this._isStack(...)` and `this._delStack(...)`.
- The only definitions found are global functions `_isStack` and `_delStack`,
  not `Websockets.prototype` methods.
- Those global functions themselves use `this._waitMsgArray`, which would not
  refer to the Websockets instance when called as ordinary globals.
- Both loops assign to undeclared `index`, creating or reusing a global.
- `_isStack` stores `this._waitMsgArray[index][0]` into `mStackOutput`; that
  appears to be the message type rather than the full queued message.
- Return state is represented internally as strings `"true"`/`"false"` before
  conversion to booleans.
- The path emits substantial per-message logging.

This is a prime resilience/performance investigation, not yet a proven
production failure. Required emulator tests:

1. context-change message with an empty wait queue;
2. focus and transition messages arriving before context change;
3. duplicate sequence numbers;
4. sequence rollover;
5. malformed and truncated JSON;
6. forced queue flush;
7. queue growth under missing counterpart messages;
8. reentrant message delivery during routing.

The likely fix is to make the helpers real prototype methods, use local loop
indices, queue structured records, and cover the ordering state machine with
deterministic traces. It should not be patched until the expected protocol has
been captured from a real CMU or generated by real MMUI services.

## Service-manager resilience

The v70/v74 `sm.conf` contains 117 service entries, 91 of which explicitly set
`reset_board="yes"`. A failure in a broad part of the system can therefore turn
into a full-CMU reboot.

The reset policy may be appropriate for genuinely load-bearing services, but it
is too costly to change speculatively. Instrument first:

- record service start time, ready time, ping latency, retry, and reset cause;
- identify the actual reboot initiator and dependency chain;
- separate critical vehicle/display services from optional media/network apps;
- use bounded restart/backoff for demonstrably isolated services;
- preserve the factory reset behavior for `jciVBS`, `jciMMUI`, audio manager,
  `jciTds`, and `jciBootManager` until bench evidence proves otherwise.

The 70-to-74 service changes should be treated as vendor guidance: Mazda added
ready flags, timeouts, shutdown persistence, and dependency changes rather than
simply removing services.

## Runtime performance candidates

Measure before changing these areas:

- synchronous or high-volume logging in UI message paths;
- repeated DOM query and layout work in list controls;
- unbounded arrays, timers, and event subscriptions across context changes;
- repeated dictionary/resource loading;
- expensive screen construction hidden behind animations;
- native-service ping storms or retries;
- storage writes to `/data` and `/data_persist` during normal interaction;
- cross-service DBus/WebSocket serialization volume.

A useful trace format should correlate:

- monotonic timestamp;
- UI app/context;
- input event;
- WebSocket sequence and message type;
- native service/event source;
- frame or transition completion;
- CPU, RSS, and I/O samples.

This lets emulator traces and CMU traces be compared without requiring exact
wall-clock equivalence.
